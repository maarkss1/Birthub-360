## 2. Finding OBSOLETED, but replaced by a new, related debt item

**DEVOPS-001 / DEVOPS-002** (Oracle Cloud deploy/backup/restore simultaneously broken by a
container-name mismatch) — **the underlying bug is moot**: commit `783f8582`
("retire oracle cloud deployment resources", 2026-09-18) deleted the entire OCI path —
`docker-compose.oci.yml`, `docs/deploy/oracle-cloud.md`, `docs/ADR/ADR-004-Producao-Oracle-Cloud.md`,
`scripts/{deploy,backup,restore}-oci.sh`, `.github/workflows/deploy-oci.yml`,
`docs/security/runbooks/DEPLOY_ROLLBACK_OCI.md`. All confirmed absent from disk.

**New finding — DEVOPS-010 (proposed ID), HIGH:** the deletion left the declared-production-path
documentation in a self-contradicting state, and nothing in that same commit fixed it:

- `render.yaml` is live (`autoDeployTrigger: commit`) — Render is the only deploy path that
  still functions.
- `docs/deploy/README.md` (last touched 2026-09-12, untouched by the deletion) still names
  Oracle Cloud / `docker-compose.oci.yml` as the "alvo definitivo de produção" and links to the
  now-deleted `oracle-cloud.md` and ADR-004.
- `docs/development/LOCAL_FIRST.md` — **edited by the very commit that deleted the target** —
  still contains a banner calling `docs/deploy/oracle-cloud.md` "o caminho canônico de
  produção," pointing at a file that commit itself removed.
- `docs/release/PRODUCTION-READINESS.md` — also edited in `783f8582` — still cites
  `oracle-cloud.md`/ADR-004 as the deploy/infra source of truth.
- `k8s/`, `argocd/`, `charts/` remain in the tree, documented elsewhere as aspirational with no
  real cluster behind them.

**Why it's a distinct debt, not just residue:** this is a fresh instance of the same root cause
the original audit already named — **RC-12, documentation drifting from the code it
describes** — introduced by the fix itself, in the same commit, same day. No file was updated to
say "Render is now canonical." A new engineer or on-call responder reading `LOCAL_FIRST.md` or
`PRODUCTION-READINESS.md` today would be pointed at infrastructure that no longer exists.

**Recommended correction (not implemented — documentation only):** update the three surviving
docs above to name Render as canonical, remove the dead links, and either delete or explicitly
label `k8s/`/`argocd/`/`charts/` as non-target/exploratory so they stop reading as a second
"real" production path.

## 3. New debt introduced since baseline (not in the original 118)

**Schema/migration drift on `organizationId` NOT NULL — HIGH, proposed ID DATA-007.**

Commit `bf9489fe` ("tornar organizationId NOT NULL e adicionar RLS cascata em models
principais", 2026-09-19 23:24 — the second-to-last commit on `main` at the time of this delta)
changed `prisma/schema.prisma` for `Company`, `Contact`, `Lead`, `Activity`, `AuditLog.tenantId`,
and `Prospect` from `String?`/optional-relation to `String`/required-relation with
`onDelete: Cascade`.

Evidence this was done unsafely:

1. **No migration was generated.** `ls -t prisma/migrations | head -1` shows the latest
   migration is `20260920000000_add_ailog_agentrole` (an unrelated column add) — there is no
   migration file altering these six models' nullability. `prisma migrate deploy` in CI/prod
   will not apply this schema change at all; the Prisma Client types and the actual database
   column nullability are now out of sync.
2. **The change bypassed its own documented precondition.** The comment removed by this exact
   diff read: *"Nenhuma linha órfã é esperada; migrar para NOT NULL + ON DELETE CASCADE ... é a
   correção pendente, **condicionada a verificar ausência de linhas NULL em produção antes de
   aplicar**."* No evidence (migration, script run, or docs note) that this verification
   happened before the schema was changed.
3. **CI has no drift gate.** `.github/workflows/*.yml` contains no `prisma migrate diff` or
   `prisma migrate status` step — nothing in the pipeline would catch schema/migration
   divergence before it reaches a deploy.

**Failure scenario:** if any of these six models have existing NULL `organizationId`/`tenantId`
rows in a real environment, a future `prisma migrate dev`/manual migration attempting to catch
the schema up will fail outright (or, worse, `ON DELETE CASCADE` on `Organization` deletion
could cascade-delete `Lead`/`Contact`/`Activity`/`Prospect` rows that previously survived
tenant deletion under the old optional relation — a data-loss change that shipped with zero
migration, zero test, and zero rollout note). This is exactly the RC-14 pattern the baseline
audit already named ("schema and application layer built at different times") — recurring in
the newest commit on the branch.

**Recommended correction (not implemented):** before this reaches any shared environment, run
the production-NULL-row verification the original comment required, generate the actual
migration (`prisma migrate dev`), and add a CI step (`prisma migrate diff --from-migrations
... --to-schema-datamodel ...` or `migrate status`) so schema/migration drift fails the build
instead of reaching prod silently.
